# 壳只呈现 harness，不改它的实现

这个仓库是 DSH 的桌面外壳，职责是把 `dsh web` 的界面装进原生窗口。因此**对 harness 行为的任何偏好都通过 profile 配置表达，不修改 `node_modules` 里的上游实现**。

配置改动可见、可版本化、随 DSH 升级存活；改依赖树则相反 —— 不可见、影响本机所有 DSH 用法、且 `npm i -g @deepseek-ai/dsh` 或切换 Node 版本即被抹掉。

## Considered Options

**直接改全局安装里的上游实现 —— 否决。**
它有一层伪装：见效最快，且不改本仓库任何代码。代价是改动落在无人版本控制的地方、波及本机每一个 DSH 用法，而且不持久 —— 于是还得配一个"重应用脚本"来兜底，那个脚本做的正是把错误做法固化下来。

**由壳在 boot 时下发 `--patch` overlay —— 否决。**
看似比改依赖树干净，但壳**会附着**到已在跑的 `dsh web`（附着与否由 `backend.rs` 的 `probe_port` 判定）。附着时壳根本不 spawn 进程，overlay 无从施加。结果是选择器行为随「附着 / 自起」而变 —— 比任何单一行为都更难预测。

**一个有纪律的补丁器（版本化、幂等、锚点保护、默认关闭）—— 是另一回事，但本仓库仍不采用。**
`dsh-tauri-desk/deepseek-harness-desktop` 走的就是这条：它在 `src-tauri/src/service/patch/alpha_auth.rs` 用锚点替换给自己补出一个 `--skip-auth` 选项 —— 幂等、锚点不匹配就安全跳过、不含该参数时普通 `dsh web` 行为完全不变。

它和第一条被否决做法的区别**不是"改没改"，而是改得可见、可重放、可安全退场**。本仓库仍不采用它，因为我们的缺口（附着时的凭证）用配置加自签 cookie 已经解掉，没有需要动上游代码的场景。但这道界线要写清楚：**被否决的是手改依赖树，不是"补丁器"这个形态本身。**

**写进用户的 profile 配置（`~/.dsh/profiles/<name>/cordis.patch.yml`）—— 采用。**
profile 无论被谁启动（终端里的 `dsh web`、还是壳）都会被读取，所以行为一致；且它属于用户配置，不是被篡改的依赖。

## Consequences

- 本仓库代码里不携带任何 harness 行为补丁；终端 `dsh web` 与窗口里的行为始终一致。
- 上游缺陷（例如 macOS 原生目录选择器在宿主窗口下拿不到 key 焦点）只能**通过配置绕开或等上游修复**。"在本仓库里就地修好它"是被本决策禁止的 —— 哪怕诊断完全正确。
- profile 配置在 `~/.dsh/` 下，不在本仓库的版本控制内，且影响本机所有 DSH 用法；换机器或重置 `~/.dsh` 后需要重新施加。
