# 领域文档

工程技能在探索本仓库代码时，应如何消费这里的领域文档。

## 探索之前先读这些

- 仓库根部的 **`CONTEXT.md`**，或
- 仓库根部的 **`CONTEXT-MAP.md`**（若存在）：它指向每个 context 各一份 `CONTEXT.md`，
  只读与你主题相关的那几份。
- **`docs/adr/`**：读与你要动的区域相关的 ADR。

这些文件若不存在，**静默继续**。不要指出它们缺失，也不要主动提议创建。`/domain-modeling`
技能（经 `/grill-with-docs` 和 `/improve-codebase-architecture` 到达）会在术语或决定真正
被敲定时惰性创建它们。

## 文件结构

本仓库是 **single-context**：

```
/
├── CONTEXT.md
├── docs/
│   ├── adr/
│   │   ├── 0001-<决定>.md
│   │   └── 0002-<决定>.md
│   ├── agents/          ← 本目录：技能配置，不是领域文档
│   └── DESIGN.md        ← 设计说明，改契约前必读
└── src-tauri/
```

## 用词表里的词汇

当你的产出要命名一个领域概念时（工单标题、重构提案、假设、测试名），使用 `CONTEXT.md` 里
定义的术语，不要漂移到用词表明确回避的同义词。

本仓库已有的固定说法值得沿用：**薄壳**、**不干扰契约**、**附着**（对应「自己起服务」）、
**启动画面**、**后端探测**。这些词在 `README.md` 和 `docs/DESIGN.md` 里含义稳定，别另造同义词。

如果你需要的概念还不在用词表里，那是个信号：要么你在发明项目不使用的语言（重新考虑），
要么这里有个真实的缺口（记下来交给 `/domain-modeling`）。

## ADR 冲突要摆出来

如果你的产出与既有 ADR 矛盾，显式点出来，而不是静默覆盖：

> _与 ADR-0002（附着而非新起服务）矛盾，但值得重开，因为……_

本仓库的契约型决定（不干扰、退出不留残留、薄壳）都带有真实的取舍代价，重开它们之前
先把 `docs/DESIGN.md` 里对应的理由读一遍。
